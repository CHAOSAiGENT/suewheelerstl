# MVP2 Design — Sue Wheeler Wood Refinishing Admin

**Date:** 2026-04-14  
**Status:** Approved  
**Scope:** Kanban pipeline board, crew roster, bid builder with copyblock library, PDF generation

---

## 1. Overview

MVP2 upgrades the admin portal from a flat request list into a full job pipeline tool. The three pillars are:

1. **Kanban board** — visual pipeline with 7 columns, drag-to-move cards, crew assignment, lost-job tracking, and quarterly archiving.
2. **Crew roster** — lightweight name-only roster for assigning people to jobs.
3. **Bid builder** — a two-panel document editor backed by a 13-category copyblock library, producing a PDF saved to the client portal and emailed on send.

## 2. Kanban Board (`/admin`)

### 2.1 Columns

| #   | Column         | Color                   | Meaning                                               |
| --- | -------------- | ----------------------- | ----------------------------------------------------- |
| 1   | To Bid         | `#11B2E8` blue          | Request received, estimate not yet sent               |
| 2   | Bid Sent       | `#A65D37` amber         | Estimate delivered, awaiting client acceptance        |
| 3   | On Deck        | `#7B5EA7` purple        | Bid accepted, scheduled, not yet started              |
| 4   | Active         | `#C5880A` gold          | Work in progress                                      |
| 5   | Finishing      | `#2A7A2A` green         | Near completion; after-photos + final payment pending |
| 6   | Fully Complete | `#2A2421` dark          | All done, payment confirmed, after-photos uploaded    |
| 7   | Lost           | `#9e9087` grey (dimmed) | Job not won; reason captured                          |

Lost is the rightmost column, visually dimmed. It stays on the board for full-pipeline visibility.

### 2.2 Status Enum Migration

Old `SubmissionStatus` → new values:

| Old               | New              |
| ----------------- | ---------------- |
| `new`, `reviewed` | `to_bid`         |
| `quote_sent`      | `bid_sent`       |
| `scheduled`       | `on_deck`        |
| `completed`       | `fully_complete` |

New values added: `active`, `finishing`, `lost`.

Full enum: `to_bid | bid_sent | on_deck | active | finishing | fully_complete | lost`

### 2.3 Card Anatomy

Each card displays:

- **Last name** (large, bold)
- **Address** — number, street, zip (e.g. `2204 Cherokee St 63118`)
- **Start date badge** — e.g. `START MAY 6` or `START TBD`
- **Bid amount** — shown if set (e.g. `$1,450`)
- **Crew tags** — names from the assigned crew roster
- **Last note snippet** — `admin_notes` field value, italic, truncated to one line

### 2.4 Drag-to-Move

Library: `@dnd-kit/core`.

On drop:

1. Optimistic UI update (card moves immediately).
2. `PATCH /api/admin/submissions/[id]` with `{ status: newColumn }`.
3. On error: revert card to original column, show toast.

**Lost move:** Dropping a card into the Lost column opens a modal before the PATCH:

- Reason (required): `price | timing | competitor | unknown`
- Note (optional): free text
- Saved as `lost_reason` + `lost_note` on the submission.

**Finishing → Fully Complete gate (soft warning):** If `after_photos_uploaded = false` OR `final_payment_confirmed = false` at drop time, show a confirmation modal listing what's incomplete. Sue can dismiss and proceed, or cancel.

### 2.5 `after_photos_uploaded` and `final_payment_confirmed`

Both are boolean fields on `submissions`. Set via two checkboxes on the `/admin/[id]` submission detail page (in the existing "Project" section). They have no hard enforcement — only the soft warning on column move.

### 2.6 Quarterly Archive

A button in `/admin/settings` labeled **Archive Completed Jobs**.

Action: sets `archived_at = now()` on all `submissions` where:

- `status IN ('fully_complete', 'lost')`
- `updated_at < now() - interval '90 days'`
- `archived_at IS NULL`

Archived cards are excluded from the Kanban board query. A toggle in `/admin/settings` reveals archived cards in a separate read-only list.

## 3. Crew Roster

### 3.1 Data Model

```sql
create table crew_members (
  id         uuid primary key default gen_random_uuid(),
  name       text not null,
  active     boolean not null default true,
  created_at timestamptz not null default now()
);
```

Names only — no roles, phone, or email.

### 3.2 Assignment

`submissions` gets a new column: `crew_member_ids uuid[] default '{}'`.

On `/admin/[id]`: multi-select from active crew members. Saved via `PATCH /api/admin/submissions/[id]` with `{ crew_member_ids: [...] }`.

### 3.3 Management UI

Panel in `/admin/settings`:

- Lists all active crew members
- **+ Add** — inline text input → `POST /api/admin/crew` → `{ name }`
- **× Remove** — marks `active = false` (soft delete, preserves history on old cards) via `DELETE /api/admin/crew/[id]`

## 4. Bid Builder (`/admin/[id]/bid-builder`)

### 4.1 Layout

Two-column layout:

**Left sidebar (240px, fixed):**

1. **Client panel** — name, address, phone, start date badge, bid amount
2. **Photos panel** — submission photos as draggable thumbnails (3-per-row grid); drag onto any document block
3. **Library picker** — category list (13 items); click a category to load its blocks below; click a block to append an instance to the document
4. **Footer** — Amount (number input) + Start Date (date picker), pinned to bottom of sidebar

**Right document area (flex: 1):**

- **Header bar**: "Estimate — [Client Name]" · block count · **Preview PDF** button · **Send to Client** button
- **Block list**: stacked editable instances (see §4.3)
- **Add hint**: dashed empty state at bottom — "← Click a block in the library to add it"

### 4.2 Copyblock Library

Source file: `/Volumes/studio/Chaos_Clients/Sue_Wheeler/_assets/Bids/Copyblock_Library_Complete.md`  
Committed to repo as: `src/lib/bid/copyblock-library.json`

The JSON is a parsed representation of the 13 library sections. Structure:

```ts
interface CopyblockLibrary {
  categories: {
    key: string; // e.g. "doors-frames"
    label: string; // e.g. "Doors & Frames"
    blocks: {
      key: string; // e.g. "front-door"
      title: string; // e.g. "Front Door"
      body: string; // default copy text
    }[];
  }[];
}
```

Block titles use clean human names — no historical occurrence counts. Updating the library means editing the JSON file and redeploying (no DB table needed; the library changes infrequently).

**12 categories:**
Doors & Frames · Staircases & Railings · Kitchens · Rooms · Lead / EPA · Furniture · Porches & Exterior · Service Types · General Modifiers & Repair Tiers · Admin Blocks · Price Benchmarks · Architectural Glossary

### 4.3 Document Blocks

Each block instance in the document:

```ts
interface BidBlockInstance {
  id: string; // local UUID for ordering
  source_key: string; // e.g. "front-door" — traces back to library
  title: string; // editable; defaults to library block title
  body: string; // editable; defaults to library block body; unique per instance
  photo_paths: string[]; // Supabase storage paths of attached photos
}
```

**Behavior:**

- Adding the same source block twice creates two independent instances.
- Editing `title` or `body` on one instance does not affect any other.
- The "from: [source name]" label next to the title is read-only traceability.
- Drag handle (⠿) enables vertical reorder within the document via `@dnd-kit`.
- ✕ Remove deletes the instance from the document (no confirmation needed).

**Photo attachment:** Dragging a thumbnail from the Photos panel onto a block's drop zone appends its Supabase storage path to `block.photo_paths[]`. Photos render inline in the PDF between the block body and the next block.

### 4.4 Persistence

**Table:**

```sql
create table bid_blocks (
  id            uuid primary key default gen_random_uuid(),
  submission_id uuid not null references submissions(id) on delete cascade,
  sort_order    int  not null default 0,
  source_key    text not null,
  title         text not null,
  body          text not null,
  photo_paths   text[] not null default '{}',
  created_at    timestamptz not null default now()
);

create index bid_blocks_submission_id_idx on bid_blocks(submission_id, sort_order);
```

Auto-saved: each title/body edit triggers a debounced `PATCH /api/admin/bid/blocks/[id]` (500ms) with `{ title, body }`. Reorder saves immediately via `PATCH /api/admin/bid/blocks/[id]` with `{ sort_order }`. Full document flushed on "Send to Client" and "Preview PDF".

### 4.5 PDF Generation

**Route:** `POST /api/admin/bid/generate-pdf`

**Library:** `@react-pdf/renderer`

**Process:**

1. Fetch all `bid_blocks` for the submission, ordered by `sort_order`.
2. For each block, fetch signed Supabase Storage URLs for `photo_paths`.
3. Render a `@react-pdf/renderer` `<Document>` with:
   - Header: client name, address, start date, bid amount
   - Each block as a section: title (bold), body text, inline photos
   - Footer: Sue Wheeler Wood Refinishing · (314) 367-6054 · suewheelerstl.com
4. Upload resulting PDF buffer to Supabase Storage: `bid-files/[submission_id]/estimate-[timestamp].pdf`
5. Update `submissions.bid_file_url` with the storage path.
6. Return the signed URL.

**"Send to Client"** button:

1. Calls generate-pdf (above).
2. Calls existing `/api/admin/bid` route with `bid_amount` + `bid_notes` (summary of block titles) + `bid_file_url`.
3. Resend email to client includes PDF as attachment.
4. Client sees PDF download link at `/my-request/[token]`.

**"Preview PDF"** button: calls generate-pdf, opens resulting signed URL in a new tab. Does not send to client.

Replaces the manual file-attach field in the current `AdminBidForm`.
